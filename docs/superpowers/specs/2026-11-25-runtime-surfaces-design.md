# Shared runtime surfaces (#202)

Build one local/injected runtime over the existing sendChatMessage executor. Keep fallback, tool policy/replay, skill activation and scoped memory in that executor. No server listeners, live Telegram, credentials provisioning, deployments or #203 work. Existing mobile calls remain supported.

Sequence: first make the text execution path importable in Node without native module mocks and add explicit cancellation. Prove the same fake scenario through mobile sendChatMessage and a real CLI process. Then expose a compact authenticated runtime and thin web/Telegram adapters. The user's request authorizes reversible design choices and staged implementation without extra approval.

Alternatives: duplicating AgentCore orchestration in a CLI would bypass fallback/replay; a hosted gateway would introduce deployment/auth infrastructure outside scope. Choose platform-neutral interfaces with lazy native defaults and per-instance storage injection where needed. CLI host composition is a deliberately trusted local module, never an argument accepted from remote clients.

Runtime sessions are created by a trusted host resolver for authenticated owners; owner identity must come from authentication, never a request namespace. The runtime assigns opaque session/run IDs, authenticates before create/start/stream/cancel/disconnect, binds records to owner and surface, and rechecks during streaming. Client requests contain bounded text only; endpoint/history/system prompt/tool approvals/skill activation/memory scope come from host configuration. Memory namespace remains a data scope, not auth. Unknown and forbidden session/run requests return the same fixed error.

Run API exposes start, stream, cancel and run convenience plus disconnect. Exactly one final outcome (completed, failed, cancelled), no raw exception details or private configuration in events. Bounded input, active runs and retained output; one consumer per run. Disconnect cancels owned runs and discards their buffers. Per-run cancellation reaches fetch and approval waits, prevents later tools/fallback/queue/memory writes, and suppresses late chunks. Dispatched external calls retain unknown outcome semantics; cancellation is not rollback.

Text output is owner-visible, but configured endpoint URLs/API keys/MCP tokens are redacted, including values split across cumulative streaming updates. Errors use static codes. Streams do not expose raw request payloads, policy objects or arbitrary telemetry. Injected auth/resolver are trusted deployment responsibilities; default adapters authenticate nobody unless explicitly configured.

CLI is a callable I/O adapter and an installed-tsx script requiring explicit trusted host module. Mobile integration is the existing real sendChatMessage path wrapped by the shared executor (no second state machine). Web and Telegram handlers accept injected connection/update contexts, never open a socket or subscribe to a bot. Telegram host auth must bind both actor and conversation, including private/group distinctions. Both adapters delegate to the same runtime.

Tests use fictitious text, injected transports and fake storage only. Acceptance: actual Node process parity; cancellation before dispatch, during fetch/stream/approval, no replay, truthful unknown tool outcome; auth first, session ownership/surface, revocation/disconnect, concurrent owners, bounded buffering, secret-safe errors/output; #198–201 regressions. No claims about live native UI, real provider cancellation, deployed identity verification or Telegram delivery.
